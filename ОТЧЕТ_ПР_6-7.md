## 1. ЦЕЛЬ И ОСНОВНЫЕ ПОНЯТИЯ

### Что такое система контроля версий?
Git — это распределенная система контроля версий. Она отслеживает все изменения в файлах и позволяет в любой момент вернуться к любому состоянию проекта.

* **Репозиторий:** папка, за которой следит Git. Вся служебная информация хранится в скрытой подпапке `.git`.
* **Индексация (`git add`):** подготовка файлов к сохранению.
* **Коммит (`git commit`):** логический «снимок» проекта с автором, датой и описанием.
* **Связывание (`git remote add`):** сохранение в файле `.git/config` имени и ссылки на удаленный сервер или другую папку на компьютере.
* **Клонирование (`git clone`):** скачивание репозитория с сервера целиком вместе со всей историей.
* **Отправка (`git push`):** передача коммитов на сервер.
* **Получение (`git pull`):** скачивание коммитов с сервера и их слияние.
* **Конфликт версий:** ситуация, когда два человека изменили одну и ту же строчку файла, и Git просит человека выбрать правильный вариант вручную.

### Задание 1. Локальное связывание двух репозиториев на ПК без GitHub
* **Что сделано командами:**
  ```bash
  # Создание второго локального хранилища
  git init --bare "C:\Users\makar\Desktop\6-7\homework\02_второй_репозиторий"

  # Связывание первого репозитория со вторым
  git remote add second_local "C:/Users/makar/Desktop/6-7/homework/02_второй_репозиторий"

  # Передача изменений
  git push second_local main
  ```
* **Как это устроено «руками»:** В папке `.git` первого репозитория открывается файл `config` через Блокнот и туда вписывается путь ко второй папке. Команда `git remote add` делает именно эту запись.
* **Объяснение результата:** Git — распределенная система. Любая папка на компьютере может служить «сервером» для другой папки.

* **Суть конфликта:** Два человека изменили одну и ту же строчку в файле `README.md`.

  1. Склонировали репозиторий «Б» в папку `04_четвертый_репозиторий_клон_Б`.
  2. В третьем клоне изменили строку и сделали `git push`.
  3. В четвертом клоне изменили ту же строку на другой текст и сделали `git push`.
  4. Git вернул отказ: `! [rejected] main -> main (fetch first)`.
  5. В четвертом клоне выполнили `git pull origin main` и получили:
     ```text

     Automatic merge failed; fix conflicts and then commit the result.
     ```
  6. Файл содержал маркеры конфликта:
     ```text

     Строка конфликта: изменение из четвертого репозитория (клон 4)

     Строка конфликта: изменение из третьего репозитория (клон 3)
     >>>>>>> 404397f2a993d782d7165b9dd925c32d42af2e65

  7. **Разрешение руками:** В Блокноте удалили стрелки `<<<<<<<`, `=======`, `>>>>>>>` и оставили объединенный текст:

     ```
  8. Зафиксировали слияние:

## 5. ОТВЕТЫ НА КОНТРОЛЬНЫЕ ВОПРОСЫ

1. **Как отправить изменения на удаленный репозиторий?**  
   Командой `git push <remote> <branch>` (например, `git push origin main`). Флаг `-u` при первом вызове запоминает привязку ветки.
2. **Как влить изменения в локальную ветку из удаленного репозитория?**  
   Командой `git pull origin main`. Она объединяет скачивание `git fetch` и слияние `git merge`.
3. **Какой командой фиксируются изменения?**  
   Командой `git commit -m "Сообщение"` (предварительно файлы добавляются в индекс через `git add <файл>`).
4. **Как используется GitHub в реальной работе?**  
   Облачный хостинг кода, командная разработка через ветки и Pull Requests, контроль качества (Code Review), учет задач (Issues, Projects) и автотесты/автодеплой (CI/CD).
5. **Опишите принцип коллективной работы с GitHub.**  
   Ветка `main` хранит стабильную версию. Каждый программист создает под задачу ветку `feature-branch`, делает коммиты, отправляет на GitHub, открывает Pull Request. Команда проверяет код и утверждает слияние (Merge) в `main`.
