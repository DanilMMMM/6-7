* **Суть задания:** Создать на компьютере второй пустой репозиторий, связать его с первым через `git remote` и передать изменения напрямую.
* **Выполненные команды:**
  ```bash
  # Создание второго пустого репозитория на локальном диске
  git init --bare "C:/Users/.../repo2"

  # Добавление локальной папки в качестве remote для первого репозитория
  git remote add second_local "C:/Users/.../repo2"

  # Отправка истории коммитов напрямую из первого во второй
  git push second_local main
  ```
* **Объяснение результата:** Git является **распределенной (децентрализованной)** системой контроля версий. Ей не обязателен центральный сервер вроде GitHub: в роли удаленного (`remote`) репозитория может выступать любая директория на локальном диске или в локальной сети. Каждый локальный репозиторий содержит полную базу данных истории проекта.


## 4. Ответы на контрольные вопросы

### Вопрос 1. Как отправить изменения на удаленный репозиторий?
**Ответ:** Командой `git push <имя_удаленного_репозитория> <имя_ветки>`. Например, `git push origin main`. Флаг `-u` (`--set-upstream`) при первом пуше позволяет связать локальную ветку с удаленной, после чего можно выполнять просто `git push`.

### Вопрос 2. Как влить изменения в локальную ветку из удаленного репозитория?
**Ответ:** Командой `git pull <remote> <branch>` (например, `git pull origin main`). Команда `git pull` является комбинацией двух действий: `git fetch` (скачивание новых объектов и ссылок из удаленного репозитория) и `git merge` (слияние скачанной удаленной ветки с текущей локальной веткой).

### Вопрос 3. Какой командой можно зафиксировать изменения в репозитории?
**Ответ:** Командой `git commit -m "Сообщение коммита"`. Перед фиксацией файлы должны быть добавлены в область подготовленных файлов (staging area / индекс) с помощью команды `git add <имя_файла>` (или `git add .` для всех файлов).

### Вопрос 4. Как используется GitHub в реальной работе?
**Ответ:**
1. **Хостинг и бэкап кода:** надежное облачное хранение истории проекта.
2. **Совместная разработка:** синхронизация работы десятков разработчиков без риска перезаписать чужой код.
3. **Code Review (Ревью кода) через Pull Requests:** проверка качества кода коллегами перед слиянием в основную ветку (`main`/`master`).
4. **Управление задачами:** вкладки *Issues* и *Projects (Kanban)* для отслеживания багов, фич и планирования релизов.
5. **CI/CD (GitHub Actions):** автоматический запуск тестов, линтеров, сборка и публикация проекта на боевые сервера при каждом пуше.

### Вопрос 5. Опишите принцип коллективной работы с GitHub
**Ответ:**
1. Основная ветка (`main` / `master`) содержит стабильный рабочий код.
2. Для каждой новой задачи разработчик создает отдельную ветку (`feature-branch` или ветку исправления бага `bugfix`).
3. Разработчик вносит изменения, делает коммиты локально и отправляет свою ветку на GitHub (`git push origin feature-branch`).
4. На GitHub открывается **Pull Request (PR)** — запрос на слияние изменений из фиче-ветки в основную.
5. Команда проводит ревью кода, автоматические тесты (CI) проверяют сборку.
6. После одобрения ветка сливается (`merge`) в `main`, а локальные копии других разработчиков обновляются через `git pull`.
